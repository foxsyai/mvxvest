# Contract review, 2026-10-12

An internal adversarial review of `contracts/vesting` at commit `37f3823`, by an
independent reviewer working in a separate checkout with no access to the
author's reasoning. Every finding came with a test that failed on that code.
The fixes keep those tests (`contracts/vesting/tests/review_*.rs`), and the
fixes themselves get a second review.

No path let a stranger take funds. Claims never paid more than vested, cancels
refunded exactly the unvested part, nothing could be claimed or cancelled twice,
and the accounting invariant held in a 1,800-step random walk against an
independent model (`review_safe_accounting_random_walk_test.rs`, kept as a
regression test).

## Findings and fixes

| # | Severity | Finding | Fix | Test |
|---|---|---|---|---|
| F1 | Medium | `recoverBouncedKeys` let the creator take a claim key whenever nothing had been claimed. A key that was delivered can come back with nothing claimed (a "claim all" that returned a key that paid nothing, then bounced), so the creator could take over even a non-cancelable vesting. | The contract records when a claim key goes through `claim` (`claimKeySeen`); the creator can only recover a claim key that never reached a holder. `init` and `upgrade` refuse payable metadata, so no other path can put a key in the contract. | `review_creator_seizes_delivered_key_test`, `admin_test::a_payable_deploy_or_upgrade_is_refused` |
| F2 | Low | An EGLD `create` took its total as "EGLD paid minus the current fee", so a fee change while the transaction was pending changed the vesting instead of failing, against the documented promise. | `create` takes the total as an argument; the payment must equal total plus fee. | `review_fee_change_egld_create_test` (adapted to the new signature: on the old code the vesting was silently 4 EGLD instead of 5) |
| F3 | Low | `getNextRelease` was empty for a linear vesting that had not started, or that releases less than a unit per second, though the docs said empty means "nothing more will vest". | Exact next release for linear curves; empty only when everything has vested or after a cancel. The property test now checks exactly that. | `review_next_release_linear_test`, `schedule_math::next_release_*` |
| F4 | Low | The creator could not recover its own bounced cancel key while the contract also held a claim key the creator may not take. | Each caller gets the keys it may take; the call fails only if it may take none. | `review_recover_cancel_key_blocked_test` |
| F5 | Info | A stepped schedule with `start == end` accepted any interval, unlike the spec. | The code follows the spec: no interval fits an empty duration. | `review_spec_stepped_interval_test` |

Also changed from the review's notes: `keyRecovered` now names which key moved
(one event per key); the collection views return empty instead of failing while
an issue is pending; the docs of the nonce views say the answer stays after a
burn.

## Noted, not changed

- A creator who names a beneficiary that cannot receive the key gets it back
  (documented in the spec, section 5; the dApp will show undelivered keys).
- A key that can pay nothing more (cancelled, everything vested already
  claimed) looks like a live key until its holder sends it to `claim`, which
  burns it. The dApp will show the state from `getVesting`.
- `cancelledAt = 0` means "not cancelled"; a block timestamp of 0 never occurs.
- The batch limit (100) is checked against measured gas in MEASUREMENTS.md.

## Second review (of the fixes above, at `b827f32`)

A second independent reviewer checked each fix and looked for anything the
fixes broke. F2 to F5 were confirmed correct, with extra passing tests that pin
them down (`review2_safe_*`). F1 was incomplete:

| # | Severity | Finding | Fix | Test |
|---|---|---|---|---|
| A | Medium | The F1 guard read the contract's own code metadata in `init` and `upgrade`. The Rust test VM writes the new account first, the Go VM (the real one) after: on the real chain every deploy failed ("account not found"), and an upgrade saw the old metadata, so an upgrade to payable passed. Reproduced with the official `mx-scenario-go` 5.1.0. | No check in `init`/`upgrade`. The metadata is read at call time: while the contract is payable, `create` is refused and the creator cannot recover claim keys. | `go_vm_test::{deploy, payable_contract}`, `admin_test::a_payable_contract_refuses_to_create_and_keeps_claim_keys_from_the_creator` |
| B | Low | The creator's recovery checked only the new flag, which vestings created before an upgrade never have. | The creator needs both: flag unset and nothing claimed. | `review2_upgrade_keeps_old_claims_unseen_test` |
| C | Low | The flag was invisible: no view, and no event for a key that paid nothing in a multi-key claim. | `claimKeyUsed` in `getVesting`; `vestingClaimed` for every key sent to `claim`. | `review2_seen_flag_not_observable_test` |

Because of A, the suite now also runs on the Go VM: `tests/go_vm_test.rs` runs
`scenarios/*.scen.json` (deploy, payable contract and repair, and a full
lifecycle with exact checks of every balance and key) with `mx-scenario-go`, in
CI too.
