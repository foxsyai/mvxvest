# dApp review, 12 October 2026

An adversarial review of the first dApp version (commit 6b0b0aa). Every finding came with a test that failed on that code. The tests now live in the dApp next to what they cover, as `review_*.test.ts(x)`, and all of them pass on the fix.

## Fourth review, of the third round's fixes (commit 2223f82), and a change of design

The fourth pass found 7 problems. All came from the same mechanism: signing a copy of a send that might be lost, at the lost send's own nonce, by removing it from sdk-dapp's store. That rests on the account's nonce not moving between the check and the post, and sdk-dapp refreshes the account and re-nonces at signing. Each round of fixes to it opened another window. So it is removed rather than patched again:

- The page never signs again a send the network did not confirm receiving, or has not seen for 2 minutes. It keeps following it, every 6 s, for as long as the page is open.
- While such a send's fate is unknown, nothing more of that creation is signed. The page explains why and offers the lines not created as a CSV (amounts written so the importer reads them back exactly). Creating them again is the creator's decision: check the explorer, disconnect and reconnect the wallet (which clears sdk-dapp's record of the lost send), then start a new creation with the file.
- send() no longer touches sdk-dapp's store. A later transaction always goes after a possibly-lost one, never in its place, and is reported under its own hash.
- Every signing panel says the same when a send goes missing: don't sign it again; reconnect the wallet before signing anything else.

The tests of findings 1, 3 and 4 (send-level copies), the review3 tests of the copy's nonce, and the review4 claim/cancel test now assert the new rule: nothing executes twice, and nothing is reported under another transaction's hash. Each revised test says so in a comment.

| # | Severity | Finding | Outcome |
| --- | --- | --- | --- |
| F1 | High | The copy of a "not found" send could move to the next nonce (sdk-dapp's refresh at signing, or the original turning up before the check), so both executed. | Removed with the copy mechanism: a lost send is never signed again. |
| F2 | Medium | A released nonce was reported as "the earlier one went through" for any transaction, so a cancel was shown as done under a claim's hash. | Removed: no substitution. A cancel after a pending claim goes at the next nonce and reports its own hash. |
| F3 | Medium | A send the API accepted that then vanished was signed again behind its own nonce. | Removed: never signed again; guidance instead. |
| F4 | Low | A refused signing forgot the lost send. | Removed with the registry. |
| F5 | Low | A line break before a formula in a label got past the export guard (semicolon locale). | Line breaks are covered like `;` and tab. |
| F6 | Low | The hint for "1.000.000" suggested a spelling that is itself refused. | Only spellings the form accepts are suggested. |

Found in the meantime, by Sebastian's own test on devnet: **My vestings failed for a wallet holding several claim keys.** sdk-core rewrites the argument array of a variadic query in place, so after `getVestings` the page's list of key nonces was corrupted, and the next lookup could not be encoded. The client now passes a copy (cb127e6). `vesting/tests/client_args.test.ts` runs the real client and sdk-core encoding, and fails without the fix. The review tests had missed it because they all mock the client.

## Fifth check, of the change of design (commit 99e5aa2)

| # | Severity | Finding | Fix | Test |
| --- | --- | --- | --- | --- |
| V1 | High | A "Sign the remaining" panel opened before a send went missing could still be signed after the page said "nothing more of this creation is signed". | Once a send of the creation is missing, every signing of it not yet sent is withdrawn (a panel whose wallet prompt is open stays). | `pages/tests/review5_Create` |
| V2 | Medium–High | A missing send was only reported once no other send of the same panel was pending, so the page went on offering the rest. | The panel reports every change of what it knows, pending included. The page records final results, and a pending one clears any earlier verdict. Pending never counts as failed. | `review5_Create` |

From the notes:

- A missing hash that comes back as pending is no longer shown as missing.
- The page warns before the tab is closed while a send is missing.
- A header line does not count toward the 5,000-line CSV limit, so the file of lines not created can be imported again.

**The reconnect is now enforced, not just advised.** While the wallet session (sdk-dapp's store) still counts a send this tab found missing, nothing new is prepared, on any page. The panel says why, and that reconnecting the wallet clears it. This closes the residual risk the check described: a creator who skips the reconnect would otherwise queue the new creation behind the lost send, and both would execute if it turned up. Tested against the real sdk-dapp store in `chain/tests/missing.test.ts`. send() still sets sdk-dapp's stored account nonce after a partial send; it no longer removes anything from the store.
